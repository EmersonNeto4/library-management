O @require_role(...) em api-auth actua como uma portagem — antes de entrar no endpoint, verifica sempre autenticação e permissões.

Decisões de implementação relevantes:

_fetch_books() — função auxiliar reutilizada pelos 3 endpoints para evitar repetição da mesma query complexa. Só o WHERE muda.
available_copies — calculado via subquery SQL (copies - COUNT(*) FROM loans WHERE return_date IS NULL), conforme exigido pelo enunciado.
STRING_AGG(DISTINCT ...) — usado para agregar autores e géneros em SQL, evitando pós-processamento em Python. O DISTINCT garante que não há repetições se os JOINs gerarem duplicados.
find_book_by_name — usa LIKE LOWER(%) para pesquisa parcial e case-insensitive.
genres no response — o STRING_AGG devolve uma string "Ficção,Terror" que é depois .split(",") em Python para gerar o array [...] exigido pelo spec. O split é a única coisa feita em Python.

melhoria fetch_books:
As duas melhorias aplicadas:

ARRAY_AGG → psycopg2 devolve list Python directamente, sem .split()
LEFT JOIN loans + FILTER → uma passagem pela tabela em vez de uma subquery por cada livro

ALTERAÇÕES — 2026-04-22 (fix imports)
─────────────────────────────────────────

Convertidos todos os relative imports para absolute imports em todos os ficheiros da api/:
  - api/app.py:              from .endpoints.X  →  from endpoints.X
  - api/auth.py:             from .db            →  from db
  - api/endpoints/*.py:      from ..auth / ..db  →  from auth / from db

Motivo: relative imports falham quando app.py é executado diretamente (python app.py).
Só funcionam quando o módulo é importado como parte de um package (python -m).
Solução: correr sempre a partir de dentro da pasta api/ → python app.py
O Python adiciona a pasta corrente ao sys.path, tornando auth e db resolvíveis.

ALTERAÇÕES — 2026-04-22 (passwords na BD)
─────────────────────────────────────────

Problema detectado: populate_data.sql inseria passwords em texto simples na tabela users.
O código em auth.py faz md5(password) antes de comparar, pelo que o login falhava
com "credenciais inválidas" mesmo com username/password corretos.

Solução aplicada directamente na BD (comando SQL no pgAdmin):
   UPDATE users SET password = md5(password);

O PostgreSQL tem a função md5() nativa que produz o mesmo hash que Python hashlib.md5().
Após o UPDATE, todas as passwords ficam armazenadas como hash MD5 de 32 caracteres hex.

Nota: novos utilizadores registados via endpoint 1 (POST /user) já ficam correctamente
com hash MD5 porque user.py aplica hashlib.md5() antes do INSERT.

Autenticação: body JSON vs HTTP Authorization header

O enunciado mostra as credenciais dentro do body JSON de cada pedido:
   {"username": "admin1", "password": "pass123", "ISBN": "978..."}

A implementação atual usa HTTP Basic Auth (Authorization header), lido via
request.authorization em auth.py. O Postman enviaria as credenciais num
header separado codificado em Base64, não no body.

Se os testes automáticos do enunciado enviarem as credenciais no body,
o mecanismo atual falha. Confirmar com o professor qual o formato esperado
antes de alterar o decorator @require_role e todos os endpoints.
