NOTAS DE ARQUITECTURA GERAL
═════════════════════════════════════════

Encriptação de passwords: hash MD5 (hashlib.md5 em Python; md5() no PostgreSQL).

@require_role(...) em auth.py actua como portagem — verifica autenticação e
permissões antes de o código do endpoint executar. Credenciais passadas no
body JSON (username + password), conforme exigido pelo enunciado.

Cada ficheiro de endpoints usa um Blueprint Flask para organizar rotas em
ficheiros separados. Todos registados com url_prefix='/sgdproj', porta 8080.

Imports absolutos em todos os ficheiros da api/ — os relative imports falham
quando app.py é executado directamente (python app.py). Solução: correr sempre
a partir de dentro da pasta api/.

Passwords na BD: o populate_data.sql inseria passwords em texto simples.
Corrigido com: UPDATE users SET password = md5(password); no pgAdmin.
Novos utilizadores via endpoint 1 já ficam com hash MD5 aplicado em Python.

_fetch_books() em librarian.py — função auxiliar reutilizada pelos endpoints
4, 5 e 6. Usa ARRAY_AGG(DISTINCT ...) para agregar autores e géneros em SQL,
e LEFT JOIN loans + FILTER para calcular available_copies numa única passagem.

11. GET /available_books_by_genre (user.py)

- Campo "raiting" respeita o typo do enunciado propositadamente.

- reviews ordenadas por review_date DESC.
- results é um array com um único objecto (o livro), conforme spec.
- Typo "coment" do enunciado corrigido para "comment".

13. POST /borrow_book (user.py)
─────────────────────────────────────────
- Acesso: qualquer utilizador autenticado (@require_role admin, librarian, reader)
- Parâmetros: user_id e ISBN no body JSON (+ credenciais de auth)

CONCORRÊNCIA — Problema e Solução:
  Race condition clássica: dois utilizadores verificam simultaneamente que há
  1 cópia livre, ambos passam na validação, ambos inserem empréstimo →
  available_copies = -1.

  Solução: SELECT FOR UPDATE (Pessimistic Locking)
  "SELECT copies FROM books WHERE isbn = %s FOR UPDATE" adquire um lock
  exclusivo sobre a linha do livro. Qualquer outra transação para o mesmo ISBN
  fica em espera até esta fazer COMMIT ou ROLLBACK. O par verificar-cópias →
  inserir-empréstimo torna-se efectivamente atómico.

  Nível de isolamento: READ COMMITTED (default PostgreSQL) — suficiente com
  FOR UPDATE, pois o lock garante leitura de dados já committed.

  Porquê FOR UPDATE e não outras abordagens:
  - SERIALIZABLE: aborta transações com erros que exigem retry logic no cliente.
  - Optimistic locking: adequado para baixa contenção; aqui a contenção pode
    ser alta (mesmo livro, muitos utilizadores).
  - FOR UPDATE: explícito, previsível, sem retry, adequado para este projecto.

  Ordem das validações (dentro da transação):
  1. SELECT copies FOR UPDATE → verifica existência + adquire lock
  2. COUNT active loans do livro → calcula available_copies
  3. available_copies > 0 (senão 400)
  4. COUNT active loans do utilizador → limite de 5 simultâneos (senão 400)
  5. Verifica se utilizador já tem este livro (a constraint unique_active_loan
     na BD também impediria o INSERT, mas assim damos mensagem clara)
  6. INSERT INTO loans → COMMIT

14. POST /report/submit_review (user.py)
─────────────────────────────────────────
- Acesso: qualquer utilizador autenticado (@require_role admin, librarian, reader)
- Parâmetros: user_id, ISBN, rating (1-5), comment no body JSON (+ credenciais)
- Condição: utilizador deve ter histórico de empréstimo do livro (activo ou devolvido)
- Lógica: upsert via INSERT ... ON CONFLICT (books_isbn, users_user_id) DO UPDATE
  - INSERT se não existe review para este par (utilizador, livro)
  - UPDATE (rating, comment, review_date) se já existe
  - ON CONFLICT actua sobre a PRIMARY KEY da tabela reviews
- rating validado em Python (1 ≤ rating ≤ 5) antes de chegar à BD
  (a constraint chk_reviews_rating na BD também o impede, mas assim a mensagem
  de erro é clara)


─────────────────────────────────────────
15. POST /return_book (user.py)
─────────────────────────────────────────
- Acesso: qualquer utilizador autenticado (@require_role admin, librarian, reader)
- Parâmetros: user_id, ISBN no body JSON (+ credenciais)
- Lógica: SELECT loan_id WHERE return_date IS NULL → UPDATE SET return_date = CURRENT_DATE
- O registo de empréstimo não é apagado — mantido para fins de relatório/histórico.
- Devolve user_id em caso de sucesso (conforme spec).
- Erro 400 se não existir empréstimo activo para o par (utilizador, livro).


─────────────────────────────────────────
16. GET /report/TopLoanedGenres12Months/<N> (librarian.py)
─────────────────────────────────────────
- Acesso: admin + librarian
- N passado na URL como path parameter (<int:n>), validado > 0.
- Filtra empréstimos dos últimos 12 meses: loan_date >= CURRENT_DATE - INTERVAL '12 months'.
- JOIN loans → books_genres → genres; GROUP BY género; COUNT(loan_id); ORDER BY DESC; LIMIT N.
- Devolve lista de {"genre": genre_name, "borrow_count": count}.

PONTOS A DISCUTIR COM PROFESSOR
═════════════════════════════════════════

1. Autenticação: body JSON vs HTTP Authorization header
   O enunciado mostra credenciais no body JSON de cada pedido.
   Implementação actual lê username/password do request.get_json().
   Confirmar se os testes automáticos esperam este formato.

2. Endpoint 11 — Mediana vs Média no rating
   O enunciado especifica "median" → implementado com PERCENTILE_CONT(0.5).
   A média (AVG) seria mais intuitiva e é o padrão em sistemas reais.
   Se aceite, trocar para AVG(r.rating) — mudança de uma linha.
